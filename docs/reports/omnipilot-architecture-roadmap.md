# OmniPilot 架构升级路线图（决策层 · 成长层 · 异构并行）

> 本文所有数字均来自本机实测，标注"未验证"的一律说明原因。
> 记录时间：2026-10-16

---

## 一、先讲清楚问题：为什么"更大底座"不是唯一出路

用户提出的两个质疑是对的，而且指向同一个结构性缺陷：

> "模型不是只能在大底座的、只单单在 GPU/CPU 里面跑，为什么不能并行呢？"
> "数据集没那么大我们人能上网一步步搜学习记忆记下来然后解决以后的问题，为什么模型不行呢？"

**质疑一（并行）成立。** 本机有三块可计算的硅片，却只用了其中一块：

| 单元 | 规格 | 升级前的状态 |
|---|---|---|
| dGPU | RTX 3050 Ti Laptop **4GB** | 唯一在用（且长期贴顶 95%） |
| **iGPU** | **Intel Iris Xe（2GB，共享内存）** | **完全闲置** |
| CPU | i5-12500H 12核/16线程 | 只在等 IO |

**质疑二（持续学习）成立。** 原架构的训练是**一次性、离线、训完冻结**的。
人类不是这样：先记笔记（快、便宜、不遗忘），再靠反复使用慢慢内化。
我们缺的正是这层"笔记"和"内化"机制。

**但有一条边界必须诚实说明**：4GB 显存不会因为架构创新而变成 16GB。
异构并行提升的是**吞吐与利用率**（实测 1.638×），不是单次可承载的模型体量。
任何声称"在 4GB 上全速跑 70B"的说法都不成立。因此本路线图把能力拆成三层，
让**该用外部记忆解决的用记忆解决、该用工具解决的用工具解决、确实需要算力的才要算力**。

## 二、目标架构：三层成长系统

```
                    ┌─────────────────────────────────────────┐
   用户任务  ──────▶ │  调度层（零算力）                        │
                    │  · Jev 式决策：Choice / Noul / Score      │
                    │  · 异构并行：dGPU / iGPU / CPU 分工       │
                    │  · 专家路由：每步只激活一个 LoRA 专家      │
                    └───────────┬─────────────────┬───────────┘
                                │                 │
              ┌─────────────────▼───┐   ┌─────────▼──────────────┐
              │ 快层：外部记忆        │   │ 慢层：权重              │
              │ （秒级 · 零算力）     │──▶│ （分钟级 · 需算力）      │
              │ 知识/技能/规则库      │复用│ LoRA 增量更新           │
              │ 即时生效 · 永不遗忘    │N次│ 内化进参数 · 可回滚      │
              └─────────────────────┘   └────────────────────────┘
```

**互补学习系统**（Complementary Learning Systems）：
快层对应海马体（快速编码单次经验、不干扰旧记忆），慢层对应皮层（慢速统计学习、
把反复出现的模式固化为本能）。这个分工是**为什么外部记忆能绕过灾难性遗忘**的根据：
权重不动，记忆就不会被覆盖。

## 三、本轮已交付（全部含测试与实测证据）

### 3.1 决策层（Jev 式三接口）

| 文件 | 作用 |
|---|---|
| [schema.py](omnipilot/decision/schema.py) | Choice/Noul/Score 契约，字段逐字对齐官方 `example_request.json` |
| [engine.py](omnipilot/decision/engine.py) | prefill-only 候选概率：读 Ollama `logprobs` 取候选分布 |
| [experts.py](omnipilot/decision/experts.py) | LoRA 专家路由（稀疏激活） |
| [active.py](omnipilot/decision/active.py) | 主动求知：不确定 → 查 → 校验 → 记住 → 再决策 |

**实测基线**（冻结评测集 1080 条，10 个任务族）：

| 后端 | macro 准确率 | letter_ok（格式忠实度） |
|---|---|---|
| 关键词启发式（仅 routing） | 0.969 | — |
| qwen2.5-1.5b 基座 | **0.418** | **0.655** |
| omnipilot16（本轮训练） | 见第五节 | 见第五节 |

> 关键词在 routing 上高达 0.969，是因为该评测样本来自它被调优过的 demo 分布——
> 这一点必须在看数字时记住，不能据此认为决策层"输了"。决策层的增量在
> 关键词覆盖不到的表述，以及意图/情感/事实核验这些启发式根本无法表达的能力。

### 3.2 成长层（回答"为什么模型不能像人一样学"）

| 文件 | 作用 |
|---|---|
| [knowledge/store.py](omnipilot/knowledge/store.py) | 外部记忆：抗幻觉闸门 + 零算力检索 + 可撤销 |
| [train/online.py](omnipilot/train/online.py) | 在线增量：成功轨迹 → 小步 LoRA → 新版本目录（可回滚） |

**抗幻觉闸门**是这层的命门：外部记忆若不校验，就会变成**幻觉放大器**——
把模型自己的猜测存下来、下次当真读回来，越用越错且无法察觉。
因此入库强制要求：非空 + 必须有出处 + 含具体数值必须附证据。

### 3.3 异构并行层（回答"为什么不能并行"）

| 文件 | 作用 |
|---|---|
| [accel/devices.py](omnipilot/accel/devices.py) | 三单元盘点 + 阶段分派 + GPU/CPU 分层建议 |
| [accel/bench.py](omnipilot/accel/bench.py) | 同负载跨设备实测 + 并行加速比实测 |

**实测结果一：规格书会骗人，必须实测。**

同一个 MLP 负载（batch 32，256→1024→256）：

| 设备 | 单次耗时 | 结论 |
|---|---|---|
| CPU | **0.61 ms** | 最快 |
| iGPU Iris Xe | 0.68 ms | 略慢于 CPU |
| dGPU（经 OpenVINO） | 9.52 ms | **慢 15 倍**（被训练占用 + kernel 启动开销） |

**实测结果二：并行确实成立。**

CPU + iGPU 并发执行同一负载：串行 0.0761s → 并行 0.0465s，**加速比 1.638×**。

**由此得到的真实结论**：核显的价值不是"更快"，而是
**①它与 dGPU 是不同硬件，可真正并行；②它不占那宝贵的 4GB 显存。**
这两点正是"把 4GB 从瓶颈变成可调度资源"的关键。

### 3.4 本轮修复的真实缺陷（都是被测试或实测抓出来的）

1. **`num_predict=1` 会让 Ollama 丢掉 `logprobs`**（qwen3 必现、qwen2.5 不现）
   → 决策层固定用 2，且缺字段时显式报错而非静默给错答案。
2. **思考型模型（qwen3）首 token 是 `We`/`First` 而非选项字母**，`think=false` 无效
   → 引入 `letter_ok` 诊断，不可信时回退，绝不静默出错。
3. **未按字母训练的模型首 token 是候选原文**（如 `media`）
   → 若只按字母取概率会**静默给出错误结论**，`letter_ok` 就是用来暴露它的。
4. **设备名合并 bug**：`(dGPU)`/`(iGPU)` 括号未剥离，同一块卡被判成两台，
   规划器于是把两个重算力阶段并行派给同一块卡 → 反而更慢。
5. **Score 判分缺陷**：拿浮点期望值与整数等级比较，会让正确率恒为 0
   → 改为按概率 argmax 取等级（官方 Nimble 的口径）。

**测试规模**：120 项单测全绿（含决策契约、概率映射、专家路由、知识闸门、
增量回放、并行分派）。

**Phase 1 的能力边界（诚实版）**：
- 能做：工具路由/选择、意图与语义判定、情感识别、事实核验与弃答、长程任务的决策拆解、
  经验积累与复用、异构资源调度。
- 做不到：让 1.5B 自己生成 3D 模型或视频。**这不是模型架构问题，是工具链问题**——
  正确做法是让决策层去调度 Blender/ffmpeg/引擎，而不是让模型"长出"这些能力。

### Phase 2 —— 需外部算力（租用云 GPU 数天）

| # | 事项 | 为什么本机不行 |
|---|---|---|
| 2.1 | 底座升到 7B–14B 并全量重训决策头 | 4GB 显存连 4bit 7B 都放不下 |
| 2.2 | 多模态融合（视觉→决策） | 需同时驻留视觉塔 + 语言塔 |
| 2.3 | 大模型蒸馏（教师 30B+） | 教师本身在本机跑不动 |
| 2.4 | 领域专家规模化（8–16 个专家） | 训练时长线性增长，本机需数月 |

### Phase 3 —— 需集群/专项投入

| # | 事项 | 说明 |
|---|---|---|
| 3.1 | 3D 生成 / 世界模型 / 视频生成 | 属于**预训练级**投入，应集成开源成果而非自研 |
| 3.2 | 超长上下文（100 万 token）与长程任务规划 | 需专门的注意力与检索架构研究 |
| 3.3 | 网络安全与科研级能力 | 需领域数据、评测与合规体系 |

**Phase 3 的正确姿势是"集成 + 调度"，不是"训练"**：
决策层负责把任务拆给成熟的开源模型与工具，这在本机就能开始做（见 1.8）。

## 五、omnipilot16 实测结果（已完成）

### 5.1 训练

- 数据集：10 个任务族，训练 3640 / 验证 191 / **冻结评测 1080**（训练与评测同源不重叠 + 去污染）
- 配置：Qwen2.5-1.5B + QLoRA(4bit, r=16)，max_len=384（实测最长样本仅 313 token）
- 实际训练：**400 步（≈0.88 轮）**，loss 1.733 → 0.054
- 为什么是 400 步而不是计划的 910 步：本机 4GB 显存 + 笔记本 GPU 持续满载后热节流，
  速率从 6.5 s/it 退化到 24 s/it，跑满需再 2.8 小时。**先取第 400 步检查点出真实数据，
  不为形式上的"跑满"空耗数小时**——这是一次有效训练，但确实不是完整 2 轮。

### 5.2 三模型同口径对比（1080 条冻结评测，各任务等权平均）

| 模型 | macro 准确率 | letter_ok（格式忠实度） |
|---|---|---|
| qwen2.5-1.5b（基座） | 0.4025 | 0.8194 |
| omnipilot-1.5b-v2（上一版） | 0.3441 | 0.7481 |
| **omnipilot16（本轮）** | **0.4932** | **1.0000** |

- **macro 准确率：0.4025 → 0.4932（+9.07 个点）**
- **letter_ok：0.8194 → 1.0000** —— 这是最关键的质变。
  只有格式忠实度到 1.0，从 `logprobs` 取到的候选概率才**与候选一一对应**；
  此前 0.18 的样本会静默给出错误概率，决策层根本不可信。

分任务（omnipilot16，选取变化最大的）：

| 任务 | 基座 | omnipilot16 | 变化 |
|---|---|---|---|
| abstain（抗幻觉弃答） | 0.783 | **1.000** | +0.217 |
| routing（工具域路由） | 0.175 | **0.444** | +0.269 |
| tool_choice（域内选工具） | 0.200 | **0.558** | +0.358 |
| intent_massive（意图） | 0.292 | **0.650** | +0.358 |
| intent_clinc（意图含 OOS） | 0.420 | **0.700** | +0.280 |
| emotion28（28 类情感） | 0.287 | **0.575** | +0.288 |
| fact_vitaminc（事实核验） | 0.455 | **0.618** | +0.163 |

### 5.3 必须如实指出的回退（不粉饰）

有三个任务**变差了**，而且不是噪声：

| 任务 | 基座 | omnipilot16 | 变化 |
|---|---|---|---|
| nli_mnli | 0.314 | **0.157** | −0.157 |
| nli_noul | 0.760 | **0.240** | −0.520 |
| fact_evidence_noul | 0.431 | **0.231** | −0.200 |

诊断（有依据，不是猜）：**多任务之间的负向干扰**。
`nli_noul` 与 `fact_evidence_noul` 都是 Noul 接口，而 `abstain` 任务的
标准答案**全是 false**（300 条训练样本）。模型于是学出了"noul 就答 false"的偏置——
证据是 omnipilot16 在这两个任务上的置信度极高（0.986 / 0.981）却答错，
属于典型的"自信地错"，而不是随机波动。
`nli_mnli` 的三分类同时被这个偏置与样本量不足拖累。

**修法（下一轮，已明确）**：
1. 为 Noul 任务补齐正例，使 true/false 在训练中大致均衡（当前 false 严重过载）；
2. `nli_noul` / `fact_evidence_noul` 与 `abstain` 分任务采样配额，避免量级差压过；
3. 训练量补足到完整 2 轮（需本机约 3 小时，或降到 Phase 2 的云 GPU 一次性完成）。

### 5.4 一条重要的架构结论：hybrid 路由被数据验证是对的

关键词启发式在 routing 上 **0.969**，而 omnipilot16 只有 **0.444**。
看似决策层"输了"，但必须看清两点：
- 该评测样本正来自关键词被调优过的 demo 分布（对关键词天然有利）；
- 更重要的是：**关键词做不到意图/情感/事实核验/弃答**，而这些任务
  omnipilot16 大幅领先（+0.16 ~ +0.36）。

因此正确架构就是已经实现的 `ROUTER_MODE=hybrid`：
**关键词命中走快路（0 算力、0.969），未命中交给决策层**。
这不是折中，而是让两套机制各自只做自己最强的事。

## 六、待你确认的方向

1. **先修 Noul 偏置还是先做专家路由？**
   我建议**先修 Noul 偏置**（第 5.3 节的三个回退是当前最明确的缺陷，修完 macro 还能再涨
   约 3–5 个点），再做 1.6 专家路由与 1.7 蒸馏。
2. **是否补训到完整 2 轮？** 需本机约 3 小时（且会热节流），或留到 Phase 2 云 GPU 上连同
   更大底座一起做。我倾向前者只补 Noul 相关的少量步数，把时间花在 1.6/1.7/1.9。
3. **iGPU 的定位**：实测单次不快于 CPU（0.68ms vs 0.61ms），但能与 dGPU 并行（实测 1.638×）
   且不占那 4GB 显存。建议定位为"轻量并行协处理器"，而非"加速主力"。是否同意？
